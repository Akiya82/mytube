# MyTube — установка

[English version](SETUP.md)

Короткая инструкция: переменные `.env`, порядок запуска, что прокинуть во
внешний реверс-прокси, как проверить кэш, бэкап и режимы кэша. Файл
намеренно минимален — со временем он вырастет в полноценный README, когда
проект начнёт публиковать образы.

Каждая команда ниже либо реально выполнена при написании этого файла на
живом стеке (`docker compose ps` — все сервисы healthy), либо помечена как
непроверенная явно.

## Что это и чего не умеет

Self-hosted раздача progressive MP4 для просмотра синхронной компанией
7–15 друзей в браузере и в плеере AVPro внутри VRChat.

Три честных ограничения:

- Каждый зритель в VRChat обязан **один раз** включить в настройках
  «Allow Untrusted URLs» — без этого AVPro не откроет ни один внешний
  адрес, включая свой собственный.
- **Публичные и group-public инстансы VRChat не поддерживаются** начиная
  с билда 1546 — только приватные и friends-инстансы.
- **Адаптивного битрейта нет и не будет.** Разные качества (если
  понадобятся) живут как разные издания одного тайтла, не как один поток
  с переключением на лету — адаптивный битрейт подтверждённо не работает
  в VRChat.

**Про `MYTUBE_S3_UPSTREAM` отдельно.** `api` ходит в хранилище по
`MYTUBE_S3_ENDPOINT`, `edge` — по `MYTUBE_S3_UPSTREAM`. Это два разных
адреса на одно и то же хранилище: если сменить один и забыть второй,
загрузка (через `api`) и выдача (через `edge`) уйдут в разные места, и
поломка вскроется не сразу, а на первом же просмотре нового тайтла. Обе
переменные меняются одновременно при смене эндпоинта хранилища.

**Внешний эндпоинт хранилища.** Есть ещё две переменные для этого случая,
но они не обязательны в `.env`, потому что по умолчанию совпадают со
значениями встроенного хранилища — свежий клон стартует и без них в
`.env`: `MYTUBE_S3_SCHEME` (`http` или `https`; встроенное хранилище —
обычный HTTP, внешний эндпоинт обычно HTTPS) и `MYTUBE_S3_HOST` (голое
имя хоста внешнего эндпоинта, намеренно **без** порта — edge использует
его и как имя SNI при TLS-рукопожатии, и как заголовок `Host` вышестоящему
серверу, а имя хоста с портом не совпало бы ни с тем, ни с другим). Все
четыре переменные (`MYTUBE_S3_ENDPOINT`, `MYTUBE_S3_UPSTREAM`,
`MYTUBE_S3_SCHEME`, `MYTUBE_S3_HOST`) меняются вместе при переходе на
хранилище, которое не является встроенным.

Отдельное ограничение: внешний эндпоинт хранилища обязан быть достижим
**только из внутренней сети владельца**. Ничто в этом стеке не
обеспечивает контроль доступа на уровне бакета — приватность хранилища
держится на его недостижимости снаружи, и публичный S3-эндпоинт с
анонимным чтением сломал бы это сам по себе, независимо от прочих
настроек.

## Сетевая шара

Шару, которую этот стек просматривает и с которой добавляет файлы, монтирует
сам стек, а не машина, на которой он работает. На хосте ничего не нужно
заранее подключать, монтировать или готовить — дайте стеку адрес и учётную
запись, остальное он сделает сам. Именно поэтому переезд на другую машину
сводится к копированию `.env`.

Четыре настройки, три из них обязательные:

```bash
MYTUBE_SHARE_URL=//192.0.2.5/media
MYTUBE_SHARE_USERNAME=readonly-user
MYTUBE_SHARE_PASSWORD=the-password
MYTUBE_SHARE_DOMAIN=
```

`MYTUBE_SHARE_URL` — адрес, записанный так, как его хочет CIFS: прямые слеши,
без завершающего. UNC-путь Windows — тот же самый адрес наоборот:
`\\192.0.2.5\media` превращается в `//192.0.2.5/media`.

`MYTUBE_SHARE_DOMAIN` оставьте пустым, если шара не в домене: для локальной
учётной записи на раздающей машине домен не просто не нужен — с ним
монтирование не пройдёт.

Шара доступна только для чтения дважды: один раз в опциях монтирования и
ещё раз на самом монтировании контейнера. Ничто в этом стеке не может
записать обратно на неё, включая неудачное добавление — исходный файл на
шаре не трогает ни один код-путь.

**Хосту нужна поддержка CIFS в ядре.** У собственной виртуалки Docker Desktop
она есть. Голому Linux-хосту обычно требуется установленный `cifs-utils`; без
него монтирование падает с `wrong fs type`.

**Две вещи, которые иначе будут стоить вам вечера:**

Монтирование происходит при старте `api`, а не когда `docker compose` читает
конфигурацию. Поэтому неверный адрес, неверный пароль или недоступный сервер —
это не ошибка конфигурации, а `api`, который не запустился, и настоящая
причина лежит в `docker compose logs api`.

Поменять любую из этих четырёх настроек потом — само по себе недостаточно.
Docker запоминает опции монтирования именованного тома в момент его создания и
дальше пользуется запомненными, так что отредактированный `.env` ничего не
изменит, пока том не выброшен:

```bash
docker compose down
docker volume rm src_share
docker compose up -d
```

## Интерфейс

Интерфейс отвечает на собственном имени хоста (`MYTUBE_ADMIN_FQDN`), через
тот же порт edge, который уже отдаёт видео. Собственного порта хоста он не
публикует — edge остаётся единственной дверью для обеих поверхностей.

Этому имени хоста нужны собственная DNS-запись и собственный сертификат на
реверс-прокси, который владелец уже держит; TLS завершается там и никогда
внутри этого стека (рабочий пример — в «Что прокинуть в реверс-прокси»
ниже). Два имени хоста — доставочное из `MYTUBE_PUBLIC_BASE_URL` и это —
обязаны быть разными именами. Разделение того, что получает зритель, и
того, что получает оператор, — это разница между двумя именами, и больше
ничего.

Кука сессии помечена `Secure`, а значит интерфейсу нужен TLS на любом
адресе, кроме loopback. Это осознанно, и адрес в LAN не предлагается как
альтернатива: порта хоста, на котором его можно было бы достать, больше
нет, и этот документ не описывает путь, который проект не поддерживает.

**Первый запуск.** Поднять стек, затем прочитать лог контейнера:

```bash
docker compose logs api
```

Он печатает ровно одну строку с полным кликабельным адресом вида
`https://<хост-интерфейса>/setup?token=<случайная строка>` — одноразовую
ссылку установки. Открыть её один раз; выбор имени пользователя и пароля
завершает установку и сразу подписывает оператора. Ссылка работает один
раз, рестарт выпускает новую, и никто, кто не может прочитать лог
контейнера, эту страницу не достанет.

Выход из системы завершает сессию именно этого браузера на сервере; другие
устройства остаются подписанными.

**Чтобы сменить пароль**, выполните это внутри контейнера. Действует сразу,
без рестарта, и подписывает все устройства — в этом и смысл:

```bash
docker compose exec api python -m orchestrator.cli reset-password
```

Команда дважды спрашивает новый пароль, печатает имя аккаунта, который
сбросила, и говорит, что все залогиненные устройства были разлогинены.

**Если аккаунт пропал, или ссылка установки истекла и ей никто не
воспользовался** — вот путь назад:

```bash
docker compose exec api python -m orchestrator.cli create-operator --username <имя>
```

Команда откажется, если оператор уже существует.

## Плейлисты

У плейлиста своя ссылка, той же формы, что у видео, но с другим префиксом:
`https://<доставочное-имя>/p/<название>`. Вставьте её в видеоплеер мира, и
ролики пойдут один за другим. Ссылка одна, и при редактировании списка она не
меняется, так что уже разосланная ссылка продолжает работать.

Три вещи про неё стоит знать заранее, до того как о них спросят в мире.

**Правки доходят до людей при следующем открытии ссылки, а не во время
просмотра.** Плеер забирает весь список один раз, в момент открытия адреса, и
до конца сессии больше за ним не обращается. Поэтому перестановка, добавление
или удаление роликов не видны тем, кто уже смотрит: они досмотрят список
таким, каким он был на момент запуска, а новый получит каждый, кто откроет
ссылку после. Это свойство плеера, а не настройка, и с этой стороны его ничем
не изменить.

**Удаление видео из библиотеки само убирает его из всех плейлистов, где оно
было.** Остальные ролики продолжают играть, пересобирать ничего не нужно. Со
стороны оператора в плейлисте остаётся помеченный пропуск на месте этого
ролика, чтобы список не поменял форму молча; уберите пропуск, когда увидите
его.

**Повтор в конце — это собственная настройка плеера мира, а не то, что делает
сервис.** Сервис отдаёт список, который заканчивается. Начнётся ли он заново,
решает переключатель в меню самого плеера, и сервис для этого не делает ничего
— список, который заканчивается, это всё, что способна выразить любая из
половин этой связки. С включённым переключателем список корректно повторяется
в распространённых плеерах. Один плеер ведёт себя иначе: в VizVid после конца
на повторе картинка застывает, а звук продолжается. Это наблюдалось на списке,
ролики которого отличаются друг от друга разрешением, частотой кадров или
раскладкой звука; будет ли то же самое на списке из однородных роликов, не
проверялось. Если кто-то жалуется на застывшую картинку на повторе, сначала
спросите, какой плеер стоит в мире, а потом уже подозревайте сервис.

**В браузере ссылка на плейлист пока не проигрывается.** Плейлисты сейчас —
возможность для VRChat. Ссылка на отдельное видео открывается в браузере как и
раньше, и ничего из перечисленного её не касается.

## Воркер конвертации

**Это опционально.** Без него добавление совместимого файла как есть (ремукс,
без перекодирования) работает точно так же, как описано выше — воркер нужен
только для конвертации несовместимого источника. Если на вашей машине нет
подходящей GPU, остальная часть раздела к вам не относится.

Для конвертации нужна вторая машина — или второй процесс на этой же — с GPU
NVIDIA, способной кодировать (NVENC), драйвером производителя и интеграцией
рантайма NVIDIA Container Toolkit, которая и даёт контейнеру доступ к карте.
Без этого последнего компонента контейнер воркера стартует, но тут же падает
при первом обращении к GPU — в логе будет ошибка инициализации CUDA/NVENC, а
не сообщение об отсутствующем драйвере, поэтому её легко принять за
неисправную карту, хотя на самом деле не хватает именно интеграции.

Поднимается вторым compose-файлом, на машине с картой:

```bash
docker compose --env-file .env.worker -f docker-compose.worker.yml up -d --build
```

Флаг `--env-file` не опционален: без него инструмент по умолчанию читает
только файл с именем `.env`, а без флага каждая обязательная переменная
ниже отсутствует, и команда падает — по разу на каждую обязательную
переменную.

Он читает переменные из собственного `.env.worker` — отдельного файла на
GPU-хосте, а **не** из копии `.env` этого сервиса. Скопировав туда вместо
этого весь `.env`, вы отдадите GPU-хосту собственный ключ хранилища
сервиса, пароль базы данных, секрет подписи и пароль шары — их все можно
прочитать из окружения контейнера; на этой машине нужны только
тринадцать переменных ниже.

| Переменная | Назначение | Требование |
|---|---|---|
| `MYTUBE_ORCHESTRATOR_URL` | Куда воркер обращается к этому сервису — со схемой, без завершающего слэша | Обязательно, значения по умолчанию нет |
| `MYTUBE_WORKER_TOKEN` | Общие учётные данные. **Должны совпадать** со значением `MYTUBE_WORKER_TOKEN` этого сервиса (см. таблицу переменных выше) | Обязательно, значения по умолчанию нет |
| `MYTUBE_S3_ENDPOINT` / `MYTUBE_S3_BUCKET` / `MYTUBE_S3_REGION` | Тот же адрес, бакет и регион хранилища, что использует сервис. Регион входит в подпись запроса, поэтому значение, отличное от заданного сервису, роняет каждую загрузку с `SignatureDoesNotMatch` | Обязательно |
| `MYTUBE_WORKER_S3_KEY` / `MYTUBE_WORKER_S3_SECRET` | **Собственные** учётные данные воркера для хранилища — под этими именами, а не `MYTUBE_S3_KEY`/`MYTUBE_S3_SECRET` | Обязательно, значения по умолчанию нет, **без отката на ключ сервиса** |
| `MYTUBE_WORKER_NAME` | Собственное имя воркера, по умолчанию — hostname машины | Опционально |
| `MYTUBE_WORKER_VRAM_MIN_MIB` | Порог свободной VRAM (МиБ), ниже которого воркер отвечает «ожидание GPU» вместо того, чтобы забрать задачу | Опционально |
| `MYTUBE_WORKER_POLL_SECONDS` | Как часто воркер опрашивает сервис в режиме простоя или ожидания карты | Опционально |
| `MYTUBE_WORKER_MAX_OUTPUT_WIDTH` | Потолок ширины кадра на выходе кодировщика | Опционально |
| `MYTUBE_SHARE_HOST_PATH` | Где на этом хосте смонтирована исходная шара — прокидывается в контейнер как read-only bind-mount | Обязательно |
| `MYTUBE_WORKER_SCRATCH_PATH` | Каталог для черновой работы с местом под большой файл плюс его собственную перезапись | Обязательно |

**Каталог для черновой работы должен принадлежать uid `10001`** — фиксированному
непривилегированному пользователю, от имени которого работает образ воркера.
Bind-mount, который инструмент создаёт для отсутствующего каталога на хосте,
принадлежит root, и этот пользователь не может в него писать. Создайте
каталог и передайте его этому uid до первого запуска:

```bash
mkdir -p ./worker-scratch
chown 10001 ./worker-scratch
```

Если пропустить этот шаг, воркер откажется стартовать: он проверяет
доступность каталога на запись до того, как забрать хоть одну задачу, и
останавливается с одной строкой, называющей этот каталог, — вместо того
чтобы забрать задачу и упасть посреди неё с сообщением, указывающим на
исходный файл.

**Собственные учётные данные воркера для хранилища должны быть у́же, чем у
сервиса, а не копией его ключа.** Ограничьте их записью объектов и отменой
многочастевой загрузки в этом одном бакете, и больше ничем — ни удаления, ни
управления бакетом. На этой машине выполняется процесс, обращающийся по сети
к двум другим системам; утёкший отсюда ключ не должен уметь ничего удалить.
Кладите его именно под `MYTUBE_WORKER_S3_KEY`/`MYTUBE_WORKER_S3_SECRET`, даже
если сервис и воркер работают на одной машине — отката на ключ сервиса нет
намеренно: переиспользование ключа сервиса здесь было бы намерением, которое
сработало, но с ровно неправильным результатом — более широкий ключ, лежащий
на машине, которую скомпрометируют первой.

**`MYTUBE_ORCHESTRATOR_URL` обязан быть тем именем хоста, на котором отвечает
сервис, а не голым IP-адресом.** Сервис проверяет, под каким именем хоста
пришёл запрос, и отказывает во всём остальном простым `400` без объяснения
причины — поэтому воркер, указывающий на IP-адрес, получает короткий отказ
на каждый опрос, и в ответе нет ни слова о том, что дело в имени хоста. Если
в логе воркера сплошные `400` и ни одна работа не забирается — это первое,
что стоит проверить.

**Исходная шара обязана быть тем же деревом на том же относительном корне на
обеих машинах.** Хранимый путь источника относительный, поэтому строка
означает тот же файл только при совпадении точки монтирования; другой корень
молча указывает каждый уже существующий путь источника не на тот файл (или в
никуда) в момент, когда конвертация попытается его открыть.

На одной машине поднять воркер — это просто второй `docker compose ... up`
рядом с первым, без изменений в нём. На двух машинах — тот же самый файл,
запущенный на той, где есть карта.

**Как понять, что воркер работает:** в библиотеке конвертация в очереди
переходит из состояния «ожидание воркера» в «в работе», как только воркер
забирает задачу. Если она не выходит из «ожидание воркера» — ни один воркер
ещё не достучался до сервиса с совпадающим токеном.

## Ёмкость хранилища

Встроенное хранилище (SeaweedFS) настроено без фиксированного числа
томов — ёмкость следует за свободным местом на диске хоста, тома растут
лениво по мере надобности, а каждый отдельный том ограничен 30 ГБ. На
практике это значит, что реальный потолок коллекции — это свободное место
на диске хоста под том данных контейнера `storage`, а не число, которое
навязывает сам стек.

Когда на хосте действительно заканчивается место, добавления начинают
падать по причине, не имеющей отношения к самому добавляемому файлу —
собственная предварительная проверка свободного места при добавлении
может при этом всё ещё проходить (она сравнивается с рабочим каталогом,
а не с бэкендом хранилища), так что на первый взгляд отказ может выглядеть
не связанным с ёмкостью. Прежде чем подозревать что-то ещё, проверьте
свободное место на диске хоста под томом сервиса `storage`.

Чтобы изменить потолок отдельного тома, отредактируйте
`-master.volumeSizeLimitMB` в `storage/entrypoint.sh` и пересоздайте
сервис:

```bash
docker compose up -d --force-recreate storage
```

**Чтение текущего использования** не требует ничего запускать: шапка
экрана библиотеки показывает суммарно занято байт (и свободно, как
только `MYTUBE_STORAGE_QUOTA_BYTES` задан реальной квотой). Для детали
сверх суммы — какие объекты не имеют ссылки из каталога, и какие адреса
каталога указывают на объекты, которых в бакете больше нет — выполните:

```bash
docker compose exec api python -m orchestrator.cli storage-audit
```

Эта команда только читает; она никогда ничего не удаляет и не меняет.
Найдя объекты без ссылок, она печатает точную команду для удаления
каждого через ваш собственный клиент хранилища — освобождение места
намеренно оставлено оператору, а не автоматизировано на основании
сравнения, которое теоретически может быть выполнено против не той пары
«каталог — хранилище».

## Предварительные требования

Прежде чем выполнится первая команда ниже, на машине нужен Docker Desktop
с Compose v2. Установите его по [официальному руководству Docker Desktop
для Windows](https://docs.docker.com/desktop/setup/install/windows-install/),
а не по копии этого руководства здесь — вторая копия чужой инструкции по
установке устаревает, и проекту пришлось бы поддерживать уже две.

Проверить установку из шелла перед тем, как продолжить:

```bash
docker version
docker compose version
```

Этот стек заведомо работает на Docker Engine 29.7.2 с Compose v5.4.0;
более старый Docker Desktop, всё ещё поставляющий Compose v1 (отдельный
бинарник `docker-compose`, через дефис, без вывода `version`, похожего на
приведённый выше) — не то, против чего написана хоть одна команда в этом
документе.

Если `docker version` сообщает, что команда не найдена, хотя Docker
Desktop установлен — его CLI не в `PATH` этого шелла: некоторые установки
Docker Desktop кладут его в директорию пользователя
(`%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin`), которая не всегда
добавляется автоматически. Добавьте эту директорию в `PATH` или откройте
новый терминал после установки.

Образ оркестратора теперь несёт `ffmpeg` и `ffprobe` внутри себя —
добавление через интерфейс или CLI не требует ничего устанавливать на
хост ради этого шага.

Помимо самого Docker, команды в этом документе запускают ещё несколько
бинарников прямо на хосте, не внутри контейнера. На машине, где стоят
только Docker Desktop и Git for Windows:

| Бинарник | Идёт вместе с |
|---|---|
| `docker`, `docker compose` | Docker Desktop |
| `bash`, `cp` | Git for Windows |
| `openssl`, `curl` | Git for Windows (его встроенный тулчейн MinGW) |
| `ffprobe` | **Ни с чем.** Нужен только для проверки декодируемости в разделе «Проверка, что отданное видео действительно декодируется» ниже — установите отдельно (например, [сборку ffmpeg для Windows](https://www.gyan.dev/ffmpeg/builds/)) и положите в `PATH` перед запуском именно этой команды. |

Собственное обещание этого документа — каждая команда в нём либо реально
выполнена, либо явно помечена как невыполненная. Установка самого Docker
Desktop и первая закачка образов этого стека не были пройдены следованием
этому документу на машине, где не было ни того, ни другого — команда
`docker compose up -d --wait` ниже запускалась только там, где образы уже
были на месте. Проверка каждого образа в реестре (`postgres:16-alpine`,
`chrislusf/seaweedfs:3.97`, `nginx:1.27-alpine`) подтверждает, что каждый
всё ещё резолвится в реальный манифест с поддержкой `linux/amd64` — это
свидетельство, что закачка должна пройти, а не запись, что она прошла.

## Порядок запуска

```bash
cp .env.example .env
# заполнить .env — как минимум MYTUBE_SECURE_LINK_SECRET, MYTUBE_S3_KEY,
# MYTUBE_S3_SECRET, POSTGRES_PASSWORD, MYTUBE_PUBLIC_BASE_URL,
# MYTUBE_ADMIN_FQDN (см. таблицу переменных выше)

docker compose up -d --wait
```

Порядок именно такой — **сначала поднять стек, а не «сначала накатить
миграции»**. База живёт в этом же compose-проекте, поэтому накатить
миграции до её подъёма физически невозможно, а отдельного одноразового
сервиса миграций в стеке намеренно нет: `docker compose up --wait` считает
выход контейнера отказом, и разовый init-сервис сломал бы именно эту
команду. Вместо этого `docker-entrypoint.sh` сервиса `api` делает `alembic
upgrade head`, затем заводит бакет хранилища (`ensure_bucket()`) при
**каждом** старте — обе операции идемпотентны, рестарт безопасен.

Проверить, что всё поднялось:

```bash
docker compose ps            # все сервисы — healthy
docker compose logs api      # ищем строку про успешную миграцию
```

Если `ensure_bucket()` не смог завести бакет через S3 API, точная команда
штатного пути для выбранного хранилища (SeaweedFS) есть в
`docs/experiments/07-object-storage.md` — выполнить её и перезапустить
`api`.

Завести первый тайтл из командной строки:

```bash
docker compose exec api python -m orchestrator.cli add \
  --file /ingest/<файл в src/ingest/> --name "<название>"
```

Команда напечатает адрес вида `/v/<слаг>`.

**Первый запуск интерфейса** описан один раз, в разделе [Интерфейс](#интерфейс)
выше — прочитайте его там перед тем, как впервые открывать хост
интерфейса.

## Заметки по развёртыванию на Windows / WSL2

Найдено при закрытии более раннего приёмочного шлюза на реальном
Windows-хосте. Ничего Linux-специфичного здесь нет — применимо только
если compose-стек работает на Windows с бэкендом Docker Desktop WSL2. Ни
одна команда в этом разделе не была пройдена следованием этому документу
от начала до конца на машине, где WSL2 изначально не был настроен —
изложенное ниже подтверждено артефактами, уже присутствующими на одном
уже настроенном развёртывании, а не записью «настроил с нуля и всё
получилось». На том развёртывании `.wslconfig` действительно задаёт
`networkingMode=Mirrored`, предпосылку, на которой держится весь этот
раздел; если у вас это не задано — ничего из этого не относится к вам.

**Опубликованный порт недоступен из LAN, хотя `docker compose ps`
выглядит нормально, а брандмауэр Windows отключён.** Если интеграция
Docker Desktop с WSL2 использует `networkingMode: mirrored`, порт edge
доступен на `127.0.0.1`, но реальный шлюз для всего, что приходит из LAN
или интернета — это **брандмауэр Hyper-V**, управляющий VM WSL, а не
брандмауэр Windows. По умолчанию он задаёт `DefaultInboundAction: Block`
и содержит только разрешающие правила для ICMP и mDNS — опубликованный
порт контейнера никогда не получает собственное разрешающее правило
автоматически. Симптом: реверс-прокси (или любая машина, кроме самого
хоста) вообще не может достучаться до edge, при этом всё работает с
`127.0.0.1`. Починка:

```powershell
# Сначала узнайте ID создателя вашей собственной VM -- не переиспользуйте
# его с другой машины, это не универсальная константа.
Get-NetFirewallHyperVVMSetting

# Ограниченный вариант по умолчанию: только указанный удалённый адрес или
# подсеть могут достучаться до порта edge. Замените
# <reverse-proxy-address-or-subnet> на адрес хоста реверс-прокси или на
# подсеть LAN, если он нужен нескольким машинам -- см. примечание по
# безопасности ниже перед запуском.
New-NetFirewallHyperVRule -Name "MyTube-Edge-8080" -DisplayName "MyTube edge (HTTP 8080)" `
  -Direction Inbound -VMCreatorId '<ваш VMCreatorId из команды выше>' `
  -RemoteAddress '<адрес-или-подсеть-реверс-прокси>' `
  -Protocol TCP -LocalPorts 8080 -Action Allow

# Неограниченный вариант -- только если edge действительно должен быть
# доступен с любого адреса, способного достучаться до этой машины вообще
# (без -RemoteAddress он по умолчанию разрешает Any):
# New-NetFirewallHyperVRule -Name "MyTube-Edge-8080" -DisplayName "MyTube edge (HTTP 8080)" `
#   -Direction Inbound -VMCreatorId '<ваш VMCreatorId из команды выше>' `
#   -Protocol TCP -LocalPorts 8080 -Action Allow
```

**Что открывает это правило.** Без `-RemoteAddress` оно разрешает входящий
TCP на порт edge с любого удалённого адреса, способного достучаться до VM
вообще — блокирующая по умолчанию поза брандмауэра Hyper-V для этого
одного порта исчезает, причём для всех, не только для реверс-прокси.
Ограничивайте его хостом реверс-прокси или подсетью LAN, как делает
вариант по умолчанию выше; неограниченный вариант оставляйте только для
случая, когда edge действительно должен быть доступен откуда угодно, чего
собственный дизайн проекта не требует — внешний трафик и так должен
приходить через собственный реверс-прокси владельца (см. «Что прокинуть в
реверс-прокси» ниже), а не напрямую в этот порт.

На одном уже настроенном развёртывании присутствует правило Hyper-V,
совпадающее с этой самой командой — то же имя, то же отображаемое имя,
тот же ID создателя этой VM — что подтверждает: эта команда (или
эквивалентная ей) была там применена; это не устанавливает, что запуск
из заблокированного состояния был напрямую замечен восстанавливающим
доступность, поскольку тест «до/после» не сопровождает это наблюдение.
На том же хосте есть и второе, более широкое правило Hyper-V, создание
которого этот документ никогда не предписывал (`VMCreatorId: Any`, без
ограничения по удалённому адресу), поэтому наблюдаемую доступность на
нём нельзя приписать одной только команде выше.

**Git Bash коверкает абсолютные пути внутри контейнера.** Запуск команды
`add` выше (или любой `docker compose exec ... --file /ingest/...`) из Git
Bash на Windows незаметно переписывает `/ingest/x.mp4` во что-то вроде
`C:/Program Files/Git/ingest/x.mp4` прежде, чем это доходит до
контейнера — автоконвертация POSIX-путей в Git Bash не знает, что путь
предназначен контейнеру, а не хосту. Добавьте префикс
`MSYS_NO_PATHCONV=1`:

```bash
MSYS_NO_PATHCONV=1 docker compose exec api python -m orchestrator.cli add \
  --file /ingest/<файл> --name "<название>"
```

Ограничивайте `MSYS_NO_PATHCONV=1` этой одной командой, а не всей сессией
шелла — экспортируя его глобально, вы заодно отключаете конвертацию путей
Git Bash для таких инструментов, как `curl -o /d/some/local/path`, которые
после этого молча не смогут записать свой локальный выходной файл, при
этом всё равно рапортуя об успехе.

**Ловушка на стороне зрителя с VPN, не дефект сервиса.** У как минимум
одного зрителя VPN-клиент («throne») пришлось переключить с режима по
умолчанию в режим TUN, прежде чем адрес вообще заработал. Если друг
сообщает, что ссылка не грузится — сначала спросите про режим его
VPN-клиента, прежде чем разбирать сервер.

## Что прокинуть в реверс-прокси

Наружу через внешний реверс-прокси владельца выставляются **два имени
хоста**, оба на **один** порт edge (`MYTUBE_EDGE_PORT`): доставочное имя
(собственный хост `MYTUBE_PUBLIC_BASE_URL`) и имя интерфейса
(`MYTUBE_ADMIN_FQDN`). Консоль хранилища и `/healthz` наружу не выставляются
ни на одном из них — edge вообще их не проксирует. Отдельного пути доступа
изнутри LAN в обход внешнего канала нет намеренно: один адрес и один
кодовый путь для всех, включая владельца — так владелец видит поломку
первым, теми же глазами, что и друзья.

**Рабочий пример, на nginx** (edge в этом репозитории — nginx, так что это
не второй синтаксис для изучения). Это пример, а не поддерживаемый
продукт — можно использовать что-то другое, но перенести эти свойства
нужно в любом случае:

```nginx
# Доставочное имя -- видео-адреса, и VRChat, и браузер.
server {
    listen 443 ssl;
    server_name mytube.example.com;   # собственный хост MYTUBE_PUBLIC_BASE_URL

    ssl_certificate     /etc/letsencrypt/live/mytube.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mytube.example.com/privkey.pem;

    location / {
        # Критично, не для красоты. Обычная дефолтная форма реверс-прокси
        # оставляет Host тем именем, которое стоит в самом proxy_pass, а
        # оно не совпадает ни с одним server_name у edge -- запрос
        # попадает в доставочный блок edge (первый в файле и неявный
        # дефолт для любого несовпавшего Host), и панель оператора
        # отвечает закачкой видео без единого объяснения.
        proxy_set_header Host $host;

        # Доставка — прогрессивное видео кусками по Range. Буферизующий
        # прокси или прокси, срезающий заголовок Range, превращает любую
        # перемотку в полную перезакачку.
        proxy_buffering off;
        proxy_http_version 1.1;

        proxy_pass http://127.0.0.1:8080;   # MYTUBE_EDGE_PORT
    }
}

# Имя интерфейса -- обязано отличаться от имени выше.
server {
    listen 443 ssl;
    server_name admin.mytube.example.com;   # MYTUBE_ADMIN_FQDN

    ssl_certificate     /etc/letsencrypt/live/admin.mytube.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/admin.mytube.example.com/privkey.pem;

    location / {
        proxy_set_header Host $host;   # причина та же, что выше

        # Кто стучится. Каждый запрос, дошедший до edge через этот прокси,
        # приходит с адресом самого прокси, поэтому без этого заголовка
        # edge считает весь интернет одним вызывающим, и ограничение
        # частоты на входе превращается в одно общее ведро: чужой перебор
        # выжжет его и запрёт вас в вашем же интерфейсе. Доставочному
        # блоку выше заголовок не нужен: там нет ограничения частоты и нет
        # интереса к тому, кто спрашивает.
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_buffering off;
        proxy_http_version 1.1;
        proxy_pass http://127.0.0.1:8080;   # MYTUBE_EDGE_PORT
    }
}
```

Edge доверяет этому заголовку только с адреса, названного в
`MYTUBE_TRUSTED_PROXY`, поэтому клиент не может подделать свой.

**Указывать нужно адрес, который видит edge, а он почти наверняка не
совпадает с адресом вашего прокси.** Docker переписывает адрес источника у
всего, что приходит через опубликованный порт, поэтому контейнер видит шлюз
своего моста независимо от того, откуда пришёл запрос, — вписать сюда
адрес прокси в локальной сети напрашивается само собой и не работает.
Значение по умолчанию покрывает диапазон, в который попадают эти шлюзы, и
обычно оно и есть верное. Посмотреть адрес самому:

```bash
docker network inspect src_edge_net \
  --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'
```

Несовпавшее значение не ломает ничего, кроме самой защиты: заголовок
игнорируется, и ограничение снова считает всех за одного. Проверить, как
именно оно считает сейчас, можно по тексту отказа:

```bash
docker compose logs edge | grep "limiting requests" | tail -1
```

`client:` — это адрес, по которому ведётся счёт. Если там адрес шлюза, а не
реального вызывающего, значит заголовку не верят.

**Обязательная проверка: внешний прокси не должен буферизовать ответ и
обязан пропускать `Range` целиком.** Это классическая грабля двух nginx
подряд — если внешний прокси собирает весь ответ перед отправкой клиенту,
`slice`-кэш работает вхолостую, а сам ответ на Range-запрос вернётся
целым файлом вместо `206`. Проверяется одной командой через внешний
домен:

```bash
curl -r 0-1048575 -D- -o /dev/null "https://<домен>/blob/<edition_id>.mp4?exp=...&sig=..."
```

Ожидается код `206` и заголовок `Content-Range` вида
`bytes 0-1048575/<полный размер>`. Код `200` с целым файлом означает, что
внешний прокси буферизует — чинить нужно на его стороне, не в compose.

## Обновление

`docker compose up -d --wait` — единственная команда подъёма, встречающаяся
в этом документе где-то ещё — **собирает образ, только если его нет.**
Существующее развёртывание, которое затянуло изменение и запустило эту
команду как есть, получает новый шаблон edge и новый compose-файл поверх
**старого** образа приложения: ни шлюза, ни экрана логина, ни первого
запуска. Если имя хоста интерфейса к этому моменту уже опубликовано, вся
поверхность оператора оказывается в публичном интернете без единой
защиты, а `--wait` рапортует, что все сервисы healthy — старый образ
действительно здоров, он просто появился раньше шлюза.

1. Затянуть изменение.
2. Добавить `MYTUBE_ADMIN_FQDN` в `.env`, если его там ещё нет. Интерфейс
   отказывается стартовать без него и называет переменную в собственном
   логе; все остальные подкоманды compose продолжают работать, пока вы это
   чините.
3. **Пересобрать и поднять одной командой:**
   ```bash
   docker compose up -d --build --wait
   ```
   `--build` здесь не опционален — приложение запечено в образ, а
   обычная форма переиспользует то, что уже есть.
4. **Проверить, что интерфейс закрыт до того, как он достижим**, с самой
   машины, с подделанным host-заголовком:
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -H "Host: $MYTUBE_ADMIN_FQDN" http://127.0.0.1:${MYTUBE_EDGE_PORT}/library
   ```
   должно напечатать `302`. Если печатает `200` — старый образ всё ещё
   работает, остановитесь и вернитесь к шагу 3.
5. Только теперь создавать DNS-запись и vhost реверс-прокси.
6. Прочитать `docker compose logs api` за ссылкой установки и завершить
   первый запуск (см. [Интерфейс](#интерфейс) выше).

Шаг 4 перед шагом 5 — в этом весь смысл: тот, кто сначала опубликует, а
проверит потом, никак не узнает, сколько времени панель была открыта.

## Откат

Откатить приложение, оставив vhost реверс-прокси прокидывающим имя
интерфейса, — это не откат, а та же самая брешь, только зашедшая с другой
стороны, и случится она на скорости, под давлением, у того, кто только что
решил, что что-то не так. Есть ещё и шаг с базой данных, у которого нет
явного симптома, пока он не убьёт контейнер.

1. **Сначала убрать vhost интерфейса из реверс-прокси.** Не DNS-запись —
   DNS кэшируется и медленный, vhost — мгновенный. В этот момент интерфейс
   перестаёт быть достижим снаружи, и всё, что происходит дальше,
   происходит на поверхности, которую снаружи никто не видит.
2. **Понизить схему до переключения образа назад:**
   ```bash
   docker compose exec api alembic downgrade -1
   ```
   Ревизия схемы этой версии неизвестна истории миграций более старой
   версии, поэтому стартовая миграция более старого контейнера не сможет
   пройти дальше неё, и контейнер умрёт с сообщением о ревизии, которую
   не может найти.
3. Переключиться на предыдущую ревизию и выполнить
   `docker compose up -d --build --wait`.
4. Убедиться, что доставка работает — ради этого и делался откат.

Интерфейс недостижим между шагами 1 и 4, и это осознанно: это единственный
порядок без окна, в котором опубликованное имя хоста стоит перед
приложением без шлюза.

## Проверка, что отданное видео действительно декодируется

`200`/`206` с правильным `Content-Length` доказывает, что механика
доставки работает — это **не** доказательство, что байты являются
воспроизводимым видео. Более ранняя приёмочная запись однажды была
провалидирована против 3 МиБ случайных байт, у которых случайно оказался
правдоподобный размер: цепочка доставки выглядела идеально, а в плеере
ничего бы не открылось (см.
`docs/experiments/02-05-avpro-redirect-and-cache.md`). Используйте
`tools/check_decodable.sh <url-или-путь>` после добавления любого нового
тайтла, чтобы убедиться, что отданные байты действительно декодируются
как видео, а не просто что запрос на них прошёл успешно:

```bash
bash tools/check_decodable.sh "https://<домен>/blob/<edition_id>.mp4?exp=...&sig=..."
```

`ffprobe` на этой машине переупорядочивает вывод `-of csv=p=0`, поэтому
скрипт разбирает `-of json` по имени поля — не «упрощайте» обратно до csv.

## Как проверить кэш

Прогреть кэш **непосредственно перед сеансом**:

```bash
docker compose exec api python -m orchestrator.cli cache-warm <слаг>
```

Записать текущее время (для `--since` ниже), провести сеанс, затем
посчитать:

```bash
docker compose exec api python -m orchestrator.cli cache-report --since <записанное время>
```

Критерий приёмки: **ноль кусков с более чем одним запросом к хранилищу**,
то есть код возврата `0`. Доля `HIT` печатается справочно — приёмочным
числом она не является: при N синхронных зрителях на холодном кэше её
теоретический потолок — `(N-1)/N`, то есть 67% на троих.

**Ненулевой код `cache-report` без списка кусков-нарушителей означает не
«всё плохо», а «мерить нечем»** — например, лог пуст или `--since`
отфильтровал всё. В этом случае первым делом проверить, что в
`edge/nginx.conf.template` для `location ~ ^/blob/` включена директива
`log_subrequest on;` — без неё nginx не логирует slice-подзапросы вообще,
и `cache-report` физически нечего разбирать.

**Честная арифметика прогрева.** Зона кэша 512 МБ при профиле 1080p ~6
Мбит/с вмещает около 11 минут видео, а `inactive` (~2 минуты по
умолчанию) выкидывает всё, к чему не обращались это время. Поэтому
`cache-warm` по умолчанию греет только начало файла — это единственное,
что прогрев реально лечит (стартовый стойл), — и по той же причине
обещание «перезапуск хранилища посреди вечера незаметен» действует ровно
в пределах окна `inactive` после того, как хранилище снова стало
доступно, а не бесконечно долго.

**При интерпретации лога вручную:** `cache-warm` шлёт свои собственные
точечные Range-запросы, и каждый из них `cache-report` привязывает к
куску, который он реально запросил, — попадание прогрева в окно измерения
стоит не больше одного запроса к хранилищу на кусок, а не ложное
нарушение. Причина по-прежнему мерить сеанс от напечатанной метки —
увидеть сам сеанс, а не растянутый на весь прогрев начальный отрезок
файла. Строки, записанные до обновления edge, которое добавило это поле
смещения, привязать нельзя — `cache-report` считает их отдельно, и если
всё окно состоит только из них, сообщает «недостаточно данных», а не
чистое прохождение. `cache-warm` печатает инструкцию с `--since` сам после
каждого прогона.

**Замечено при проверке на живом стеке:** `$time_iso8601` в логе имеет
разрешение в одну секунду. Если записать `--since` и тут же, в ту же
секунду, начать сеанс — хвост прогрева и начало сеанса могут попасть в
один и тот же таймстемп и дать точно такое же ложное нарушение. На
реальном сеансе (минуты между прогревом и тем, когда компания
действительно смотрит) это не встречается — упомянуто здесь только
потому, что при автоматической проверке этого файла воспроизвелось
у самого исполнителя.

## Бэкап и восстановление

**Почему это есть уже сейчас:** видеофайлы можно залить заново, историю
слагов — нет. Сервис `db-backup` в `docker-compose.yml` раз в сутки
снимает `pg_dump` в сжатый файл с датой в имени, кладёт в
`./data/backups` на хосте (то же дерево `/data/`, что уже в
`.gitignore`) и удаляет дампы старше `MYTUBE_BACKUP_KEEP_DAYS` дней.

**Теперь каталог дампов содержит хэш пароля оператора** и заслуживает
такой же заботы, как любой другой секрет на машине — относитесь к
`./data/backups` соответственно, в том числе на любой машине, куда его
копируют.

Разовый прогон вручную (например, прямо перед рискованной операцией):

```bash
docker compose exec db-backup bash /backup/backup.sh --once
```

**Восстановление** (проверено на живом стеке в реальном случае — дамп
восстановлен поверх **непустой** базы, все слаги вернулись, ссылка
играет):

```bash
# 1. Остановить api. Это не формальность: шаг 3 роняет таблицы, и api,
#    держащий к ним соединения, на этом завершится.
docker compose stop api

# 2. Убедиться, что база поднята
docker compose up -d --wait db

# 3. Восстановить последний дамп.
#    ON_ERROR_STOP=1 обязателен: без него psql проглатывает все ошибки и
#    выходит с кодом 0, то есть полностью провалившееся восстановление
#    рапортует об успехе.
LATEST=$(docker compose exec -T db-backup sh -c 'ls -t /backups/mytube-*.sql.gz | head -1')
docker compose exec -T db-backup sh -c "gunzip -c $LATEST" \
  | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"
echo "код возврата: $?"   # 0 — восстановлено; иначе НЕ восстановлено

# 4. Поднять остальное. api без этого шага не вернётся сам.
docker compose up -d --wait
```

**Что даёт восстановление:** аккаунт оператора переживает восстановление,
ни одна сессия — нет: дамп хранит определение таблицы сессий, но не её
строки, поэтому на восстановленном стеке никто не остаётся залогинен, и
все входят заново, включая устройство, с которого дамп снимался.

**Восстановление дампа, снятого до появления логина у интерфейса** — и
вероятный случай, и, без этой заметки, выглядящий как непонятная
поломка. В таком дампе нет ни таблицы `operator_credential`, ни таблицы
`sessions`, поэтому он не роняет ни ту, ни другую — но восстанавливает и
номер версии схемы, каким он был на момент снятия дампа. Стек после этого
поднимается с уже стоящими обеими таблицами (их создала миграция этой
версии раньше) и версией схемы, которая их не знает; миграция написана так,
чтобы это пережить, — именно это держит контейнер живым. Что видит
оператор дальше — интерфейс без аккаунта. Перезапустите контейнер `api`,
прочитайте `docker compose logs api` за свежей ссылкой установки и
выберите пароль заново, как при любом другом первом запуске.

Дамп снимается с `pg_dump --clean --if-exists`, поэтому он самодостаточен:
кладётся и на пустую базу, и поверх существующей. Это важно, потому что
восстанавливаются, когда данные **есть** и они неверны, а не когда их нет.

**Дампы, снятые до появления этого флага, поверх непустой базы не лягут** —
упадут на первом `CREATE TABLE ... already exists`. Снимите свежий дамп
(`--once` выше) и проверьте, что восстановление проходит, до того как он
понадобится всерьёз.

**Под Git Bash на Windows** команды с путём внутри контейнера требуют
префикса `MSYS_NO_PATHCONV=1`, иначе `/backup/backup.sh` превращается в
`C:/Program Files/Git/backup/backup.sh`.

## Если что-то не так

Каждый симптом ниже новый — появился вместе с собственным именем хоста и
логином у интерфейса; ни один не объясняется самой ошибкой.

- **Панель отдаёт закачку видео вместо страницы** — реверс-прокси не
  сохраняет исходный host. См. рабочий пример в разделе
  [Что прокинуть в реверс-прокси](#что-прокинуть-в-реверс-прокси).
- **Контейнер интерфейса не стартует, лог называет переменную** —
  `MYTUBE_ADMIN_FQDN` отсутствует в `.env`.
- **Контейнер интерфейса не стартует, лог говорит, что два имени хоста
  совпадают** — `MYTUBE_ADMIN_FQDN` и `MYTUBE_PUBLIC_BASE_URL` обязаны быть
  разными именами, иначе nginx направит все запросы к этому имени в тот
  блок server, который выигрывает точное совпадение, незаметно ломая
  второй.
- **Любой адрес отвечает коротким роликом вместо страницы** — имя хоста
  интерфейса попадает в доставочный блок; либо его нет в `.env`, либо оно
  не совпадает с vhost реверс-прокси.
- **Браузер не удерживает вход** — кука сессии помечена `Secure`, адресу
  нужен TLS.
- **Ссылка установки говорит, что больше не действительна** — контейнер
  перезапустился и напечатал новую; прочитайте `docker compose logs api`
  ещё раз.
- **Полностью потерян доступ** — см. две команды с учётными данными в
  разделе [Интерфейс](#интерфейс): `reset-password`, если аккаунт всё ещё
  существует, `create-operator`, если нет.
- **Слишком много попыток, и запросы начинают отклоняться** — edge
  ограничивает частоту на маршрутах логина и установки; подождите минуту.

**Более удачный первый шаг, чем разбор списка выше:**
`bash tools/smoke_auth.sh` проходит весь путь аутентификации на живом
стеке и печатает строку прохождения или провала на каждый шаг.

## Режимы кэша

`MYTUBE_CACHE_MODE` выбирает между `edge/cache-memory.conf.template` и
`edge/cache-off.conf.template`:

- **`memory`** — рабочий режим. `proxy_cache` в tmpfs (`/dev/shm`),
  ключ кэша `$uri$slice_range` (без `$arg_sig`/`$arg_exp` — иначе кэш
  делился бы по подписи каждого зрителя, и общий просмотр компанией не
  экономил бы ни одного запроса к хранилищу).
- **`off`** — кэш выключен полностью. Нужен для диагностики: если
  поведение (например, число запросов к хранилищу) отличается только в
  `memory`, проблема в самом кэше, а не в `slice`/подписи/хранилище.

Переключение — сменить `MYTUBE_CACHE_MODE` в `.env` и перезапустить
`edge`: `docker compose up -d --wait edge`.
